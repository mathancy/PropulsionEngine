# PropulsionScript C++ runtime

`PropulsionScriptRuntime.h` is the small runtime that code generated by `propc cpp` stands on. See
SPEC.md section 11 for the design.

## Using it in PropulsionMKI

The editor runs scripts with the **interpreter**, not generated C++, so changing a script never needs a
rebuild. Scripts are plain `.prop` files in the project's `Scripts/` folder, read when Play starts: edit,
save, press Play.

`propulsion-ffi/` is a small crate that wraps the interpreter in a C interface (`propulsion-ffi/include/propulsion_ffi.h`),
built as `propulsion_ffi.dll`. Build it once with `cargo build --release -p propulsion-ffi`. The engine's
`CMakeLists.txt` finds it next to the engine folder (or `-DPROPULSIONSCRIPT_DIR=<path>`), links it, and copies the
DLL beside the executable.

The engine side lives in `PropulsionMKI/src/scripting/PlayMode.cpp`:

- A host of C callbacks gives scripts keyboard input and the level name; `print` and calls on systems that don't
  exist yet (`do Play on Audio`, `do Create on UI`, ...) go to the debug console. `do SetPaused on Game
  paused:true` really pauses: the scripts stop advancing until it is set back.
- `PlayMode::start` loads every script the scene's objects use (all in one session, so they can see each
  other), spawns one entity per scripted object at its position, rotation and scale, and refuses to start,
  with the problems and their line numbers in the console, if any script has a mistake.
- Each frame, `propulsion_step` runs the scripts and each object's transform is copied back into its `SceneObject`,
  with `make Visibility.Shown false` hiding it (`propulsion_get_flags`) and `make Collision.Enabled false` making it
  non-solid. After the scripts run, the engine's physics (`include/physics/PlayPhysics.h`, called from
  `Engine::stepPlayPhysics`) moves characters against the scene's solid shapes and hands the position back to the
  script (`PlayMode::setPosition`). It also tells scripts about overlaps (`propulsion_touch`) and a character being
  blocked (`propulsion_hit`) between scripted objects (`PlayMode::reportTouch` / `reportHit`), and answers a script's
  `trace` from the shapes of everything solid in the scene through the host's `trace` callback
  (`PlayMode::setTraceProvider`). Damage (`propulsion_damage`) isn't reported by anything yet.
- **Input is data** (modeled on Unreal's Enhanced Input; `include/input/`, `src/ui/InputAssets.cpp`). Each **Input Action**
  is an asset (`.pinputaction`: a name, a Button or an Axis), and an **Input Mapping** (`.pinputmap`) is a table of
  `action <- key` rows with Negate and Scale. An Object picks the mapping it is played with, and each read of an input
  from a script (`pressing` / `axis` callbacks, which carry the asking entity) is answered from that Object's mapping
  (`InputMap`, in `PlayMode`). The compiler is told the project's actions (`propulsion_set_input_actions`), and the editor also
  writes them to `Scripts/inputs.propapi` for `propc` and the language server. A project with no actions gets defaults
  that reproduce the old fixed keys (`include/input/DefaultInput.h`).
- **Scripts belong to Object assets**, like a Blueprint class. The Object editor's **Script** section picks a
  file from `Scripts/`, creates a starter script (**New Script**), opens it in your editor (**Open**), and
  checks it (**Check**). The choice is saved in the `.pobj` file (v3, `include/project/ObjectFile.h`). When
  Play starts, each scene instance runs the script of the Object it was placed from. An Object with no
  script just exists and is rendered; nothing runs for it.
- **The Object editor's Script section** has **Edit Graph**, which opens the script as a node graph in its own
  tab (SPEC section 12). It uses the same canvas as the material editor, with script nodes added
  (`include/nodes/ScriptNode.h`, `src/nodegraph/ScriptNodeRenderer.cpp`). `ScriptGraphEditor` loads the graph
  through `propulsion_graph_load`, sends every edit through `propulsion_graph_edit` (which only saves a valid script),
  and rebuilds from the result, so the graph and the file can't disagree. Typing in a node's field, dragging a
  white execution arrow to reorder, right-clicking to add nodes or compute a pin with a value node, and Delete
  all work. Changing the file in a text editor updates the open graph.
  The **Code** button opens the script's text beside the graph (`src/scripting/CodeBuffer.cpp` is its editing model).
  Selecting a node marks its lines and clicking a line selects its node; the text can be typed in, and text that
  parses is saved through `propulsion_graph_edit`'s `set_source` once typing pauses (one undo step), while text that
  doesn't is marked where `propulsion_graph_check_source` says it stops and is not saved. The file stays the truth:
  any other change to it replaces text typed but not yet saved.
- `tests/script_graph_test.cpp` (`cmake --build . --target ScriptGraphTest`) runs the editor headless with a
  real ImGui context and simulated mouse and keyboard: layout of every example, edits, typing into a field,
  and dragging a wire. `--shots <folder>` also writes PNGs of a few graphs.
- **The player script** (`behaviors/player.prop`) is the reference for a controllable Object: it reads the `moveForward`,
  `moveRight`, `lookX` and `lookY` axes and the `jump` button and moves and turns itself; the engine's Character Movement
  (an Object component) does the standing, falling, wall sliding and the jump. `PlayModeTest` plays it against a real floor.
- The editor's **Play** menu item snapshots the scene first and restores it on **Stop** (Escape also stops).

## Generated C++ (for shipped games)

`propc cpp a.prop b.prop --out <dir>` writes C++ for the scripts and everything they need, plus
`PropulsionScriptRegistry.generated.cpp`, which finds each script by path (`FindScript("Scripts/Door.prop")`).
That is the route for a packaged game, where scripts are compiled in for speed. The tests below check that it
behaves exactly like the interpreter the editor uses. The editor doesn't use it.

## Tests

`tests/differential.cpp`, `tests/differential_examples.cpp` and `tests/differential_kits.cpp` run the same
scenarios as the Rust interpreter's tests against generated code (the last one covers the nodes taken from
`Documentation/NODELIST.md`: math, lists, flow, damage, attaching, enums, structs, traces). `cargo test --test codegen` builds and runs them with MSVC.
